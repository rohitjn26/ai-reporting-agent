# Eval cases, explained

A walkthrough for explaining how the agent's evals work. The whole design rests on
one rule: **don't assert data values, assert relationships to the schema.** A test
that says "output must equal `orders.total_revenue`" dies when the data changes. A
test that says "the query matches what this prompt implies, using fields that exist"
works on any dataset, forever.

---

## 1. Anatomy of a case

Cases are generated by `generate.py` (see `README.md`). Each one is a prompt plus an
answer key. Example — the prompt *"order count by status"*:

```json
{
  "prompt": "order count by status",          // the ONLY thing the agent sees
  "expected": {                                // the query it SHOULD build
     "measures": ["orders.count"],
     "dimensions": ["orders.status"]
  },
  "expected_chart_types": ["bar", "table"],    // any of these is acceptable
  "expected_mapping": {                        // how save_graph should map axes
     "label_dimension": "orders.status",
     "series_measures": ["orders.count"],
     "series_dimension": null
  },
  "cube": "orders", "template": "measure_by_dimension", "source": "title"
}
```

- **`prompt`** — sent to the agent. Everything else is the answer key.
- **`expected`** — the "correct" Cube query, compared to the agent's actual `query_cube(...)`.
- **`expected_chart_types`** — a *set*, because chart type has legitimate flexibility
  (a breakdown can be a bar or a table). Grading passes if the agent's type is in it.
- **`expected_mapping`** — only used when the case exercises `save_graph`.
- **`template` / `source` / `cube`** — labels for reporting pass-rate *per category*.

`source` is one of: `title` (prompt built from the field's title — the easy case),
`synonym` (built from a description synonym like "how many orders" or "sales"), or
`llm_paraphrase` (an LLM reworded a title case into natural phrasing — see
`paraphrase.py`; the expected query is copied, so it stays auto-labelled). The
latter two test whether the agent maps oblique language to the right field.

---

## 2. How a case is used (lifecycle)

```
prompt ──► [run the real agent] ──► it calls query_cube(measures=[...], dimensions=[...])
                                          │
                              extract that actual call
                                          │
                       grade_query(actual, expected)  ──►  pass / fail
```

Plus, on every run, `members_exist(actual, metadata)` checks the agent didn't invent a
field — an invariant that needs no answer key and holds on any schema.

---

## 3. What passing and failing actually look like

Real output from running `grading.py` on hand-written agent answers:

```
CASE: A1  correct                       "order count by status"
  EXPECTED : {"measures":["orders.count"],"dimensions":["orders.status"]}
  AGENT DID: {"measures":["orders.count"],"dimensions":["orders.status"]}
  query checks : {measures: True, dimensions: True, time_dimensions: True}
  VERDICT  : PASS ✅

CASE: A2  correct + a sort nobody asked for
  AGENT DID: {... , "order":{"orders.count":"desc"}}
  query checks : {measures: True, dimensions: True, time_dimensions: True}
  VERDICT  : PASS ✅          # extras aren't penalised when the case didn't ask

CASE: A3  WRONG-but-real field (day_count instead of count)
  AGENT DID: {"measures":["orders.day_count"], ...}
  query checks : {measures: False, ...}
  VERDICT  : FAIL ❌          # the failure "fields exist" alone would MISS

CASE: A4  HALLUCINATED field
  AGENT DID: {"measures":["orders.num_orders"], ...}
  query checks : {measures: False, ...}
  hallucination: ["unknown measures: ['orders.num_orders']"]
  VERDICT  : FAIL ❌          # caught by the query check AND the invariant

CASE: B1  correct top-5           "top 5 status by order count"
  EXPECTED : {... "order":{"orders.count":"desc"}, "limit":5}
  query checks : {measures: True, dimensions: True, time_dimensions: True, limit: True, order: True}
  VERDICT  : PASS ✅

CASE: B2  forgot the limit
  AGENT DID: {... "order":{"orders.count":"desc"}}   # no limit
  query checks : {... limit: False, order: True}
  VERDICT  : FAIL ❌          # "top 5" without a limit is wrong

CASE: C1  computed measure via synonym    "revenue per unit by category"
  AGENT DID: {"measures":["order_items.revenue_per_item"],"dimensions":["order_items.category"]}
  query checks : {measures: True, dimensions: True, time_dimensions: True}
  VERDICT  : PASS ✅          # oblique wording resolved to the real computed field
```

### The teaching table

| # | Prompt | What the agent did | Verdict | Why |
|---|---|---|---|---|
| A1 | order count by status | right query | ✅ | measures + dimensions match |
| A2 | order count by status | right query **+ unasked sort** | ✅ | `order`/`limit` only checked when the case requires them |
| A3 | order count by status | used `day_count` (**real but wrong**) | ❌ | `measures: False` — the miss a membership check can't catch |
| A4 | order count by status | used `num_orders` (**made-up**) | ❌ | caught twice: `measures: False` + hallucination |
| B1 | top 5 status by order count | query + `order desc` + `limit 5` | ✅ | ordering/limit required and present |
| B2 | top 5 … | forgot `limit` | ❌ | `limit: False` |
| C1 | revenue **per unit** by category | synonym → `revenue_per_item` | ✅ | computed measure resolved from oblique words |

The point: it **passes** correct answers and harmless variation, and **fails** the two
failure modes that matter — *wrong-but-real field* (A3) and *invented field* (A4).

## 4. The important subtlety — score aspects separately (D1 vs D2)

Both build the **same correct query** for *"monthly order count split by status."* They
differ only in the `save_graph` **mapping** — which field is the x-axis:

```
CASE: D1  pivot correct
  query checks : {measures: True, dimensions: True, time_dimensions: True}
  chart type   : agent='line' allowed=['line','bar']  pass=True
  mapping      : {label_dimension: True, series_measures: True, series_dimension: True}  pass=True

CASE: D2  pivot but axes swapped (status on x-axis, months as the series)
  query checks : {measures: True, dimensions: True, time_dimensions: True}   # query still fine
  chart type   : agent='line' allowed=['line','bar']  pass=True
  mapping      : {label_dimension: False, series_measures: True, series_dimension: False}  pass=False
```

D2's **query is correct** but its **mapping is wrong**. So D2 is:

> **query = PASS, chart type = PASS, mapping = FAIL.**

The lesson: **never collapse an agent run into one boolean.** Score it on independent
aspects and report each:

1. did it build the right **query**? (A / B / C)
2. did it avoid **hallucinating** fields? (A4)
3. was the **chart type** acceptable? (D)
4. did **save_graph** map the axes right? (D2)

Report pass-rate *per aspect, per template*. A mapping regression (D2) then shows up as
"pivot mapping accuracy dropped" even while query accuracy stays 100%. A single blended
number would have hidden it — that's the trap.

---

## 5. Why it's portable

Scroll back through every case: **no assertion mentions a data value or a row count.**
Every check is *"does the agent's query/mapping match what this prompt implies, using
fields that exist in the live schema?"* Swap in a different dataset, re-run
`generate.py`, and the same output shape appears with `patients`/`ward` instead of
`orders`/`status`. **The grading code never changes.**

---

## Presenting it in 3 beats

1. **A1** — it passes the obvious thing.
2. **A3 / A4** — it fails the two real dangers: *wrong-but-real field* and *invented field*.
3. **D1 / D2** — why you score aspects separately (query vs mapping), not one pass/fail.
